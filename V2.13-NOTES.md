# Appbit V2.13

V2.13 fixes the Hostinger build failure reported against `pages/api/[[...path]].js`.

## Root cause

The V2.11 API bridge mixed CommonJS `require()` with Next.js `export` syntax while `package.json` explicitly forced the entire package to `"type": "commonjs"`. Hostinger's Webpack build rejected that route before a new deployment could replace the older live build. V2.12 moved the route to `.mjs`, but the latest Hostinger log still identified the old `.js` route, proving the deployed source did not reach the V2.12 route layout.

## V2.13 repair

- Uses one and only one Hostinger API catch-all: `pages/api/[[...path]].js`.
- The route now uses standard Next.js module syntax only (`import`, `export const config`, `export default`).
- Removed the package-wide `"type": "commonjs"` declaration so the Next.js compiler is not told to classify the route as CommonJS.
- Removed the V2.12 `.mjs` catch-all to eliminate duplicate/ambiguous API entries.
- Restored `pageExtensions` to the normal JavaScript/JSX set used by this project.
- Added a `prebuild` guard. A deployment now fails immediately with an Appbit-specific message if a legacy catch-all reappears or two catch-all API routes coexist.
- Keeps `next build --webpack`, the `.next/server` metadata finalizer, native Hostinger Next.js runtime, MySQL, LiteAPKs, Publishing, Update Center, and R2 features unchanged.
- Node 24 is supported by the package engine range and is not the cause of this module parse failure.

Visible version: **V2.13**.
